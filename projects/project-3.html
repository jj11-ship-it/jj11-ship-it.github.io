项目背景与问题

核心问题

多工具切换，出差规划效率低；企业差旅规则复杂，容易超标；行程修改会引发预算与日程连锁变化；规划结果与报销整理相互割裂

关键挑战

  • 自然语言需求存在缺失与歧义；
  • 规划需要同时满足时间、空间、预算、政策和个人偏好；
  • 多个 Agent 之间需要保持状态一致；
  • 模型、外部工具和真实数据均存在不稳定性
产品目标：让用户通过自然语言提出需求，由系统完成信息澄清、制度匹配、预算估算、行程规划、方案修改和报销核查，降低出差任务的操作成本与决策负担。

关键产品决策

01

从自由协商收敛为可控工作流

早期设想采用五角色联盟与 Agent 间谈判，后续收敛为 Intent、Application、Planning、Expense 四智能体状态机，优先保证任务链路稳定、职责清晰和结果可验证。

02

明确 LLM、Tool 与 Code 的边界

LLM负责意图理解、信息抽取和软决策；Tool负责获取交通、酒店、地图、天气和票据信息；Code负责日期、金额、制度、时间冲突和空间可达性等确定性判断。

03

采用局部修改而非整体重生成

用户修改酒店、会议时间或交通偏好时，系统先判断影响范围，只重新规划受影响的资源和日期，尽量保持其他内容不变。

04

为模型输出设置多层可靠性保障

通过结构化输出、Schema校验、候选反查、有限重试、规则兜底和人工补充，降低模型幻觉与错误结果污染已有状态的风险。

PRD 摘要

01

用户与核心场景

目标用户：有明确差旅制度约束、需要独立完成行程规划与报销的企业员工，典型用户包括销售、咨询顾问和项目人员。

核心场景：自然语言发起出差｜生成出差申请与粗预算｜上传票据并完成报销核查

02

核心功能需求

  • Intent Agent：识别新建出差、修改方案、报销和闲聊意图；提取人员、日期、城市、事项和偏好；仅针对缺失的必要信息进行追问。
  • Application Agent：识别人员差旅级别；匹配交通、住宿和补贴标准；查询参考价格；生成出差申请和粗预算。
  • Planning Agent：生成全局行程骨架；查询交通、酒店、地图和天气；选择关键资源；生成逐日安排；完成时间、空间、政策和预算校验。
  • 方案修改：理解用户修改要求；定位目标事件；判断影响范围；仅重算受影响的日期或资源；保留未受影响内容并记录版本差异。
  • Expense Agent：解析和分类票据；检查日期、金额和差旅制度；识别缺失票据；计算可报销金额、超额金额和异常项。
  • 可靠性机制：结构化输出｜Schema校验｜候选反查｜有限重试｜规则兜底｜状态保护｜人工补充｜异常降级
03

产品范围与优先级规划

P0｜核心任务闭环：意图识别｜信息抽取与澄清｜差旅制度匹配｜预算估算｜交通酒店查询｜逐日行程生成｜规则校验与异常兜底

P1｜任务延续与结果优化：自然语言修改方案｜影响范围分析｜局部重规划｜票据识别与分类｜报销合规核查｜任务状态持久化｜Trace记录

P2｜完整产品交付：前后端接口接入｜执行过程实时展示｜日历与文件导出｜邮件能力｜真实预订能力｜用户偏好与长期记忆

04

核心验收标准

  • 需求理解：正确识别四类用户意图；已提供的信息不重复询问；用户明确事实不被模型覆盖。
  • 行程规划：固定事项完整保留；不存在时间冲突和空间不可达；交通、酒店均来自真实候选或明确标注的降级数据；方案符合制度和用户偏好。
  • 方案修改：修改要求落到正确事件；受影响内容正确更新；无关日期和事件保持不变；修改后重新完成全局校验。
  • 报销核查：票据分类、合规判断和金额计算正确；能够识别缺失、超标和异常票据；无法判断的结果明确提示人工确认。
  • 异常恢复：模型或工具失败时能够有限重试或安全降级；失败结果不得覆盖已有有效状态；任务可从最近有效状态继续执行。

AI 能力边界与评测

能力边界

AI 能够完成

  • 自然语言意图识别
  • 用户需求与偏好抽取
  • 缺失信息判断与问题生成
  • 政策语义理解
  • 候选交通和酒店的综合选择
  • 逐日行程与自由事件规划
  • 自然语言修改要求定位
  • 票据类型判断
  • 用户提示与结果说明

AI 不能独立完成

  • 保证外部信息真实和实时
  • 精确计算日期、费用与补贴
  • 可靠判断时间冲突和空间可达性
  • 自由生成不存在的航班、车次或酒店
  • 在缺少关键信息时替用户做高风险决定
  • 保证方案是全局最优解

评测指标

结果质量

关注系统最终是否正确完成用户任务，避免只根据语言表达是否自然判断效果。

  • 任务完成率：是否完成信息收集、差旅申请、行程规划或报销检查等目标
  • 关键信息准确率：时间、地点、人数、预算、员工等级等信息是否提取正确
  • 规则合规率：交通、住宿、餐补等结果是否符合企业政策与预算
  • 方案可执行率：行程是否不存在时间冲突、资源错误或关键环节缺失

过程质量

关注多智能体系统是否通过正确、稳定的链路得到结果。

  • Agent路由正确率：任务是否进入正确Agent，流转顺序是否合理
  • 工具调用正确率：工具选择、调用参数及返回结果的使用是否正确
  • 状态一致率：用户约束在追问、Agent切换和方案修改过程中是否完整保留
  • 异常处理成功率：信息缺失、工具失败或需求修改后，任务能否恢复并继续执行

交付物与复盘

主要交付物

  • 多智能体职责划分与路由设计
  • LLM 与代码分工策略
  • 分层兜底与质量链机制
  • 独立评测集、稳定性复跑与人工校准
  • 事实溯源与状态保护

复盘

  • Agent数量不等于产品能力早期方案强调多角色协商，但随着业务流程细化，发现部分角色只是工具能力或确定性计算。最终将天气归入工具层、预算归入业务规则，并收敛为四智能体状态机。Agent应由独立业务判断和状态职责决定，而不是为了体现“多智能体”而增加角色。
  • 异常处理需要在设计阶段前置模型格式错误、工具无结果、政策文件异常和计划冲突不是边缘情况，而是Agent产品的常态。结构化校验、有限重试、规则兜底、状态保护和人工补充需要在工作流设计阶段就被纳入。
  • 评测不能只看最终答案一个方案看起来合理，并不代表执行过程正确。评测需要同时覆盖结果质量和过程质量，结合最终方案、Workflow路径、State传递、工具调用、异常恢复、执行时间与成本进行判断。
